## Check 4 — Employees With Working SSH Keys

```
ruth1@DESKTOP-DD7VGNC:~/Technova-Homelab$ echo "Employees with SSH keys: $count"
Employees with SSH keys: 79
```

**Discrepancy investigated:** expected 78 (3 manual + 75 automated), but the count returned 79. Full username list was pulled to identify the extra:

```bash
for username in $(getent passwd | awk -F: '$3 >= 1000 && $3 < 65534 {print $1}'); do
    if sudo test -f "/home/$username/.ssh/id_ed25519"; then
        echo "$username"
    fi
done
```

**Finding:** the extra key belongs to `ruth1` — the WSL host account, not a TechNova employee. This key exists outside of Task 2 and Task 3's provisioning entirely (never generated by either process, likely present from separate account setup at some point). Since `ruth1` was explicitly excluded from Task 3's automated provisioning by design, this is not a provisioning error — it's simply an account outside the scope of "employee keys" that happens to also have one.

**Corrected figure:** 78 genuine employee keys + 1 non-employee (`ruth1`) = 79 total key files on the system, matching expectations exactly once properly accounted for.
